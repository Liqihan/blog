# Agent 面试知识点 #017：Context Window 为什么成为瓶颈？

## 摘要

Context Window，通常翻译为上下文窗口。

它指的是模型在一次推理中能够参考的全部 Token 范围。

对于 Agent 来说，进入这个窗口的不只是用户问题，还可能包括：

```text
System Prompt
历史对话
Working Memory
长期记忆检索结果
MCP 工具定义
工具调用结果
网页正文和 DOM
截图或文档
代码文件和 diff
子 Agent 返回结果
本轮需要预留的输出
```

因此，Context Window 很快就会从一个“模型参数”，变成整个 Agent 系统的资源瓶颈。

可以把问题简化为：

```text
Agent 可以访问的信息越来越多，
但模型每一轮真正能够高质量使用的信息仍然有限。
```

即使模型支持更大的窗口，也不代表：

```text
所有信息都能被同等准确地利用
可以没有成本地反复发送
任务状态可以永久保存在里面
越接近窗口上限，效果就一定越好
```

所以，Context Window 的核心矛盾不是“能不能塞进去”，而是：

```text
在有限的注意力、成本和延迟预算里，
应该让模型在当前这一轮看到什么。
```

---

## 问题

Context Window 为什么会成为 Agent 的瓶颈？

为什么更大的上下文窗口，仍然不能替代 Memory、RAG、State 和 Runtime？

名义上的最大窗口，为什么不等于系统真正可用的有效上下文？

---

## 面试官在考什么？

这个问题表面上是在问模型最多支持多少 Token。

但面试官真正想考的是：

> 你是否理解 Context Window 是 Agent 每一轮推理的稀缺计算资源，并且能从容量、效果、成本、延迟、状态管理和安全几个层面设计上下文系统。

一个只会调用模型的系统，通常会采用最直接的方式：

```text
把所有历史继续追加
把检索到的文档全部放进去
把所有工具 Schema 一次性注册
把每次工具结果完整回传
把代码库里相关文件全部读取
```

任务短的时候，这种做法可能还能工作。

任务一旦变长，就会出现：

```text
请求超过窗口上限
关键要求被历史信息淹没
模型重复调用已经执行过的工具
旧状态和新状态发生冲突
单轮响应越来越慢、越来越贵
压缩后又丢失重要约束
```

因此，Context Window 不是单纯的模型能力问题。

它最终会变成 Context Engineering 和 Agent Runtime 的核心设计问题。

---

## 核心知识点

### 1. Context Window 是单次推理预算，不是长期记忆

Context Window 只决定模型当前这一轮能够参考什么。

它不代表模型天然拥有跨任务、跨会话的持久记忆。

可以这样区分：

```text
Context Window：这一轮模型能看到什么
Short-Term Memory：当前任务暂时保存了什么
Long-Term Memory：任务结束后仍然保存什么
State：系统执行到什么阶段
```

例如 AI Coding Agent 当前读取了一个代码文件。

文件内容进入 Context 后，模型可以在这一轮分析它。

但下一次会话是否还能使用这份信息，取决于 Runtime 是否把文件、结论或索引保存在外部系统中，而不是取决于模型窗口有多大。

所以：

```text
Context 是计算时输入，
Memory 和 State 是系统持久化能力。
```

把 Context Window 当成数据库，最终一定会遇到状态丢失和成本失控。

---

### 2. 名义窗口不等于有效窗口

模型声称支持某个长度，只能说明请求在协议和模型结构上可以被接收。

它不代表模型在整个范围内都能稳定完成：

```text
精准检索
多跳推理
跨文档比较
冲突消解
长距离因果关联
复杂状态追踪
```

长上下文研究里经常出现一个现象：

```text
关键内容放在开头或结尾时表现较好，
放在长上下文中间时，召回和推理能力下降。
```

这通常被称为 Lost in the Middle。

更复杂的评测也发现，模型通过简单的“针尖检索”测试，不代表它能在同样长度下稳定完成多条信息聚合和多步推理。

因此，工程上需要区分：

```text
Nominal Context：模型允许的最大 Token 数
Effective Context：在当前任务上仍能稳定产生正确结果的范围
```

真正应该评估的是后者。

---

### 3. 更长的 Context 会增加成本、延迟和资源占用

Agent 的每一轮调用，通常都需要处理本轮输入中的大量 Token。

上下文越长，常见影响包括：

```text
输入 Token 成本增加
首 Token 延迟增加
模型推理资源占用上升
KV Cache 占用增长
并发能力下降
超时和限流风险增加
```

Prompt Cache 可以降低重复前缀的部分成本和预处理延迟。

但它没有让这些信息从 Context Window 中消失。

也就是说：

```text
缓存解决的是重复计算问题，
不是上下文容量和信息质量问题。
```

一个被缓存的超长 System Prompt、工具列表或历史对话，依然会占用模型能够处理的窗口空间。

---

### 4. Agent 的 Context 膨胀速度远高于普通对话

普通 ChatBot 主要积累用户消息和模型回答。

Agent 还会积累大量执行信息：

```text
工具 Schema
工具参数
工具返回值
网页内容
终端日志
文件内容
代码 diff
错误堆栈
截图和视觉 Token
计划和反思结果
子 Agent 交接内容
```

例如一个 Browser Use Agent，只执行几步操作，就可能产生：

```text
页面 Accessibility Tree
DOM 摘要
截图
点击结果
网络请求
表单字段状态
页面跳转后的新内容
```

如果每一轮都把这些信息完整保留，Context 会迅速被低价值过程数据占满。

因此 Agent 的关键能力不是“获取更多上下文”，而是能够不断淘汰已经失去决策价值的信息。

---

### 5. 信息越多，噪声、冲突和注意力竞争越严重

Context 中的信息并不是彼此独立的。

它们可能存在：

```text
重复
过期
冲突
来源不明
置信度不同
作用域不同
恶意指令
```

例如：

```text
旧记忆说项目使用 npm
当前 package.json 已经改成 pnpm
历史对话要求修改公共 API
本轮用户明确要求保持兼容
网页正文中包含 Prompt Injection
```

如果 Runtime 只是把所有内容拼接起来，模型需要在一次推理中自己完成来源判断、时效判断、权限判断和冲突消解。

Context 越长，这个问题越严重。

所以高质量 Context 需要包含：

```text
来源
时间
作用域
优先级
可信度
是否已验证
```

上下文管理不是单纯的 Token 管理，也是信息治理。

---

### 6. Context 中混合了不同生命周期的信息

Agent 的输入里，常常同时存在：

```text
长期稳定的系统规则
用户长期偏好
当前项目约束
当前任务目标
最近一次工具结果
临时页面状态
一次性验证码
```

这些信息的生命周期完全不同。

如果全部依赖 Context Window 保存，就会出现两个问题：

```text
该长期保留的信息被截断
该及时删除的信息长期残留
```

例如，用户的硬约束可能在任务开始时提出，却在滑动窗口中被删除。

而一段已经消费完的长日志，可能因为处于最近几轮而持续占用大量 Token。

因此，Context 不能只按时间顺序管理，还需要按信息类型和生命周期分层。

---

### 7. 输出、推理和工具定义也会竞争同一个预算

很多系统只统计聊天历史，却忽略其他占用。

实际上，模型请求通常还需要为以下内容留出空间：

```text
System Prompt
安全规则
Tool Schema
检索结果
模型输出
结构化结果
工具调用参数
推理或中间状态
```

如果输入已经接近窗口上限，就可能出现：

```text
没有足够空间输出完整答案
工具参数被截断
代码补丁生成不完整
结构化 JSON 无法闭合
任务在最后一步失败
```

所以 Runtime 不能把窗口全部分配给输入。

它需要提前预留 Output Budget 和安全余量。

---

### 8. Multi-Agent 会放大 Context 的复制成本

Multi-Agent 系统里，常见错误是让每个 Agent 都收到完整上下文。

例如：

```text
主 Agent 有 50K Token 历史
三个子 Agent 各复制一份
子 Agent 返回长结果
主 Agent 再把全部结果重新拼接
```

这会导致：

```text
成本成倍增加
无关信息在 Agent 之间扩散
不同角色的状态互相污染
敏感信息被过度共享
主 Agent 汇总时再次超出窗口
```

A2A 或 Agent Team 的上下文交接，应该是最小任务包，而不是完整记忆复制。

Context Window 越大，如果缺少边界，系统反而越容易养成“全部发送”的坏习惯。

---

## 工业界方案

### 1. Runtime 建立明确的 Context Budget

成熟系统不会等到请求失败后才处理窗口问题。

它会在每一轮调用前计算预算：

```text
总窗口
- 预留输出
- 固定 System Prompt
- 安全规则
- 必要 Tool Schema
- 安全余量
= 本轮可分配上下文
```

然后再给不同信息分配额度：

```text
目标与硬约束：固定保留
Working Memory：高优先级
最近交互：有限保留
检索结果：按相关性分配
工具结果：摘要或引用
长期记忆：按需召回
```

这使 Context 从“消息堆积”变成可调度资源。

---

### 2. 使用分层 Context，而不是一个无限增长的消息数组

常见分层方式是：

```text
Pinned Context
必须始终保留的系统规则、目标和硬约束

Working Context
当前计划、事实、假设、下一步动作

Retrieved Context
本轮从 Memory、RAG 或文件系统按需读取的信息

Recent Context
最近几轮对话和工具交互

External Artifacts
完整代码、网页、日志、截图和文档
```

每一轮由 Context Compiler 按任务需要重新组装。

这样可以让同一个任务在较小窗口中持续运行，而不是依赖完整历史始终在线。

---

### 3. 将原始数据外部化，只把索引和结论放进 Context

对于大文件、长日志、网页和截图，工业界更常见的做法是：

```text
原始内容保存在文件系统、对象存储或 Artifact Store
Context 中保存摘要、路径、ID 和关键位置
需要验证时再局部读取
```

例如 AI Coding Agent 不需要一直携带完整仓库。

它可以保留：

```text
当前修改文件
相关符号
关键诊断
当前 diff
测试失败位置
文件索引
```

真正需要查看实现时，再调用文件读取或代码检索工具。

这也是 AI Native Software 里“模型按需读取环境”比“把环境一次性塞进 Prompt”更可扩展的原因。

---

### 4. MCP 工具需要动态发现和按需加载

一个 MCP Host 可能连接很多 Server，每个 Server 又暴露大量 Tool Schema。

如果把所有工具定义同时传给模型，工具本身就会占用大量 Context，并增加选错工具的概率。

更合理的方式是：

```text
按任务选择 MCP Server
先检索工具目录
只加载候选 Tool Schema
调用完成后清理大体量结果
资源内容按 URI 再次读取
```

MCP 解决的是工具和资源如何标准化交换。

Host Runtime 仍然需要决定哪些工具、哪些结果应该进入当前 Context。

---

### 5. AI Coding 和 ACP 采用工作集模型

编辑器 Agent 最适合采用类似 IDE Working Set 的方式。

本轮优先提供：

```text
当前文件
当前选区
相关符号定义
诊断信息
当前 diff
项目规则
任务计划
```

而不是提供整个代码仓库。

当用户切换文件或任务阶段时，Runtime 重新编译 Context。

ACP 负责在编辑器和 Agent 之间交换会话、文件和操作信息；真正决定哪些内容进入模型窗口的，仍然是 Agent Runtime 的 Context 策略。

---

### 6. Browser Use / Computer Use 保留状态，不保留全部现场

环境操作类 Agent 需要把页面内容压缩为可执行状态：

```text
当前页面或窗口
任务相关控件
已填写字段
已执行动作
是否提交成功
异常和重试次数
下一步动作
```

完整截图、DOM 和 Accessibility Tree 可以保存在外部。

特别需要保留幂等信息：

```text
提交按钮已经点击
尚未确认成功
禁止再次提交
```

否则一旦旧页面信息被压缩掉，Agent 可能重复付款、重复发送或重复创建记录。

---

### 7. A2A 只传递最小必要的 Handoff Context

Agent 之间交接任务时，可以使用结构化任务包：

```json
{
  "task": "检查支付回调的幂等问题",
  "constraints": ["保持外部 API 兼容"],
  "confirmed_facts": ["重复请求来自不同 Worker"],
  "artifacts": ["src/payment/callback.ts"],
  "expected_output": "根因、修改方案和验证用例",
  "acceptance_criteria": ["并发重试只处理一次"]
}
```

子 Agent 不需要看到用户所有历史，也不需要读取主 Agent 的全部长期记忆。

这既降低 Token 成本，也减少状态污染和权限泄露。

---

### 8. 用有效上下文评测，而不是只看最大长度

工业界评估模型或 Agent 时，不应该只记录：

```text
最大支持多少 Token
```

还应该测试：

```text
关键信息位于不同位置时的召回率
上下文变长后的任务成功率
多文档冲突消解能力
多跳推理和信息聚合能力
工具结果增多后的决策准确率
长任务中的约束保持率
Token、延迟和成本曲线
压缩与恢复后的状态一致性
```

最终要回答的是：

```text
在真实 Agent 工作负载下，
系统能稳定利用多少上下文？
```

这才是有效窗口。

## 常见误区

### 误区一：模型窗口足够大，就不需要 Memory

Context 是单次推理输入，Memory 是跨任务的持久化系统。两者解决的问题不同。

### 误区二：能塞进窗口，就说明模型能准确使用

最大长度只是容量指标，不代表长距离召回、聚合和推理能力不会下降。

### 误区三：Prompt Cache 可以扩大 Context Window

缓存可以降低重复计算的成本和延迟，但缓存内容仍然占用上下文空间。

### 误区四：RAG 检索越多，答案越可靠

检索结果过多会引入噪声、冲突和无关内容。RAG 仍然需要排序、去重和预算控制。

### 误区五：只删除最早的消息就能解决问题

最早的信息可能是用户目标和硬约束，最近的信息也可能只是无价值日志。

### 误区六：所有工具都应该一次性注册给模型

过多 Tool Schema 会占用窗口，并增加工具选择难度。工具应该按任务动态发现和加载。

### 误区七：Multi-Agent 可以通过共享完整上下文提高协作

完整共享会放大成本、污染状态并扩大权限边界。协作应该传递最小必要任务信息。

### 误区八：窗口越满，模型掌握的信息越多，效果越好

过长 Context 会增加注意力竞争和信息冲突。上下文质量通常比上下文数量更重要。

## 面试加分答案

如果面试官问：

> Context Window 为什么成为瓶颈？

可以这样回答：

```text
Context Window 是模型单次推理能够参考的 Token 预算。对 Agent 来说，系统指令、历史对话、Working Memory、工具定义、工具结果、代码、网页、截图、检索文档和输出空间都会竞争这个预算。

它成为瓶颈，不只是因为存在最大 Token 上限。第一，名义窗口不等于有效窗口，长上下文中的信息召回、冲突消解和多步推理会下降；第二，输入越长，成本、首 Token 延迟和推理资源占用越高；第三，Agent 的工具调用会快速产生大量日志、Schema 和环境信息；第四，Context 中混合了长期规则、任务状态和临时页面信息，单靠消息历史无法可靠管理生命周期。

更大的窗口只能把问题推迟，不能替代 Memory、RAG、State 和 Runtime。我会让 Runtime 建立 Context Budget，把内容分成固定保留、当前工作集、按需检索、最近历史和外部 Artifact。代码、网页、日志和截图保存在外部，只在 Context 中留下摘要、引用和定位信息；MCP 工具按需加载；A2A 只传递最小 Handoff Context；AI Coding 和 ACP 根据当前文件、选区、diff 和诊断动态编译上下文。

评估时也不能只看模型声明的最大长度，而要测试不同位置的信息召回、长任务约束保持、多文档推理、工具调用后的成功率，以及成本和延迟曲线。

所以 Context Window 真正的瓶颈，是模型能够接收的信息增长得很快，但每一轮能够低成本、高质量、无冲突地使用的信息仍然有限。
```

---

## 一句话总结

Context Window 是 Agent 每一轮推理的稀缺信息预算，真正的系统能力不在于把更多内容塞进去，而在于持续选择、组织、外部化并恢复当前最有价值的信息。
