# Agent 面试知识点 #016：Agent 如何做上下文压缩？

## 摘要

Agent 的任务越长，对话、工具调用、网页内容、代码文件、截图和执行日志就越多。

如果把所有内容原样放入模型 Context，会出现：

```text
超过模型上下文窗口
单次调用成本和延迟持续上升
旧信息干扰当前判断
关键约束被大量日志淹没
模型在长上下文中找不到真正重要的信息
```

因此 Agent Runtime 需要做上下文压缩。

可以把它理解为：

```text
在不破坏任务连续性的前提下，
用更少的 Token 保留继续完成任务所必需的信息。
```

它不是简单地把前面的消息删掉，也不是定期生成一段聊天摘要。

真正可靠的上下文压缩，需要回答四个问题：

```text
哪些信息必须原样保留？
哪些信息可以结构化提取？
哪些信息可以摘要或移出 Context？
被移出的信息以后如何重新找到？
```

所以，上下文压缩本质上是 Runtime 对任务状态进行重新编译，而不只是对文本进行缩写。

---

## 问题

Agent 如何做上下文压缩？

截断、滑动窗口、摘要、检索和状态提取分别适合什么场景？

为什么压缩做得不好，会让 Agent 看起来像突然失忆？

---

## 面试官在考什么？

这个问题表面上是在问如何节省 Token。

但面试官真正想考的是：

> 你是否理解 Agent 的 Context 是有限资源，并且能在压缩后继续保留任务目标、关键约束、执行状态、证据来源和恢复能力。

一个长任务通常会不断产生新信息：

```text
用户补充要求
模型分析和计划
MCP 工具返回
Browser Use 页面内容
Computer Use 截图
AI Coding 读取的代码
Shell 执行日志
子 Agent 的中间结论
```

如果 Runtime 只会不断追加消息，系统最终一定会遇到上下文上限。

但如果它粗暴删除历史，又可能丢失：

```text
用户明确说过的禁止事项
已经排除的失败方案
一次关键工具调用的结果
当前修改涉及的文件和符号
提交操作是否已经执行
子 Agent 结论的证据来源
```

因此，优秀的压缩策略不是“保留最近的信息”，而是“保留对下一步决策最重要的信息”。

---

## 核心知识点

### 1. 上下文压缩的目标不是更短，而是任务可继续

压缩后的 Context 至少需要回答：

```text
当前目标是什么？
有哪些不可违反的约束？
任务已经做到哪一步？
已经确认了哪些事实？
哪些方案已经失败或被排除？
有哪些关键文件、页面或产物？
还有哪些问题没有解决？
下一步准备做什么？
```

如果压缩结果很短，却无法回答这些问题，它就不是有效压缩。

例如，一个 AI Coding Agent 在压缩前已经发现：

```text
目标：修复订单重复创建
约束：不能修改公共 API
事实：重复请求来自不同 Worker
已排除：前端重复点击
当前假设：幂等锁只在单进程内生效
关键文件：src/order/create.ts
下一步：检查分布式锁的 key 和过期时间
```

压缩后必须保留这些任务状态，而不需要保留此前所有搜索过程和完整测试日志。

---

### 2. 需要先建立 Context Budget

Runtime 不应该等到模型报错以后才开始压缩。

它需要提前为不同信息分配预算：

```text
系统指令和安全规则
当前用户目标与约束
Working Memory
最近对话
工具定义
工具结果
检索内容
预留输出空间
```

可以简化为：

```text
可用输入预算
= 模型上下文上限
- 预留输出 Token
- 固定系统信息
- 安全余量
```

压缩触发条件也不应该只有“达到最大 Token”。

常见触发点包括：

```text
达到预算阈值，例如 70% 或 80%
完成一个任务阶段
工具结果突然膨胀
准备把任务交给子 Agent
任务暂停并准备写入 Checkpoint
模型或工具发生切换
```

阶段性压缩通常比临近上限时一次性压缩更稳定。

---

### 3. 截断和滑动窗口只适合低价值历史

最简单的方法是删除旧消息，只保留最近若干轮。

```text
完整历史
↓
保留系统指令 + 最近 N 轮消息
```

它适合：

```text
闲聊型对话
前后依赖较弱的请求
已经把关键状态写入结构化 State 的任务
```

它不适合：

```text
长时间代码修改
多步骤表单操作
涉及审批或支付的 Computer Use
依赖早期约束的复杂任务
```

因为“旧”不代表“不重要”。

用户第一轮提出的限制，可能比最近一轮工具日志更重要。

---

### 4. 摘要压缩要围绕任务状态，而不是聊天流水

普通聊天摘要经常写成：

```text
用户先提出了一个问题，Agent 进行了分析，
之后调用了几个工具，双方又讨论了下一步方案。
```

这种摘要对继续执行几乎没有帮助。

Agent 的压缩摘要应该采用任务结构：

```json
{
  "goal": "修复订单重复创建",
  "constraints": ["保持公共 API 兼容"],
  "confirmed_facts": ["重复请求来自不同 Worker"],
  "decisions": ["使用分布式幂等锁，而不是进程内锁"],
  "failed_attempts": ["前端防抖不能解决服务端重试"],
  "artifacts": ["src/order/create.ts", "test/order.concurrent.spec.ts"],
  "open_questions": ["锁过期时间是否覆盖最长处理时长"],
  "next_action": "检查锁 key 和 TTL"
}
```

这样的摘要更像可恢复的任务快照。

---

### 5. 结构化提取通常比自由文本摘要更可靠

不同信息的压缩方式应该不同：

```text
目标和硬约束：原样保留
已确认事实：结构化提取
决定和失败方案：生成任务摘要
代码、网页、截图：保留外部引用
最近交互：保留原文
旧过程信息：摘要或删除
长期可复用知识：写入 Long-Term Memory
```

尤其是以下内容，不能只依赖自然语言摘要：

```text
金额、日期、ID、文件路径
接口参数和返回值
已提交或未提交状态
权限和审批结果
测试通过或失败结果
```

这些信息适合进入结构化 State，避免摘要模型改写关键值。

---

### 6. 大型内容应该外部化，而不是硬塞进 Context

上下文压缩不等于所有内容都要变成摘要。

对于代码文件、网页 DOM、截图、长日志和文档，更合理的方式是：

```text
原始内容保存在 Artifact Store
Context 中只保留引用、摘要和定位信息
真正需要时再按需读取
```

例如：

```json
{
  "artifact_id": "log_20260713_001",
  "type": "shell_output",
  "summary": "并发测试 100 次出现 12 次重复订单",
  "location": "artifacts/test-output.log",
  "relevant_lines": "420-468"
}
```

这样既能减少 Token，又保留了追溯原始证据的能力。

---

### 7. 压缩必须保留来源和可追溯性

摘要可能遗漏信息，也可能把模型推测写成事实。

所以重要结论最好带有来源：

```text
事实：接口返回 403
来源：tool_call_128 的 HTTP Response

假设：账号缺少写权限
来源：Agent 推断，尚未验证
```

如果压缩只留下结论，不保留证据引用，后续 Agent 就无法判断：

```text
这是用户确认的要求？
工具返回的事实？
还是模型自己推测的？
```

压缩不能把不确定性压没。

---

### 8. 压缩后需要验证，而不是直接继续执行

一次压缩本身也是有损操作。

Runtime 可以在压缩后执行检查：

```text
目标是否仍然存在？
所有硬约束是否保留？
当前计划是否和事实一致？
是否保留未完成动作？
工具调用与工具结果是否成对？
关键 ID、金额、路径是否发生变化？
是否错误地把假设升级为事实？
```

对高风险任务，还可以让另一个模型或规则引擎检查压缩结果。

因此，上下文压缩应该被视为一次状态迁移，而不是普通文本生成。

## 工业界方案

### 1. Runtime 建立分层 Context Compiler

成熟系统通常会把 Context 组装成一条流水线：

```text
原始对话、Memory、工具结果、环境状态
                    ↓
              Context Budgeter
                    ↓
         必保留 / 可压缩 / 可移出分类
                    ↓
     State Extractor + Summarizer + Artifact Store
                    ↓
             Retrieval / Rerank
                    ↓
          生成本轮 Model Context
```

其中：

```text
Budgeter：计算 Token 和预留空间
State Extractor：提取目标、约束、事实和状态
Summarizer：压缩旧过程
Artifact Store：保存完整原始内容
Retriever：需要时找回被移出的信息
Context Compiler：生成本轮最终输入
```

这比直接把消息数组传给模型更可控。

---

### 2. AI Coding：保留状态和引用，不要压缩掉代码事实

AI Coding Agent 的 Context 里经常包含大量代码和测试输出。

更稳妥的策略是：

```text
始终保留任务目标和不可修改边界
保留当前 diff 和正在修改的符号
保留测试失败摘要与关键报错行
完整代码文件留在工作区，按需重新读取
完成的探索过程压缩为结论
失败方案进入 failed_attempts
```

例如不要把一段具体代码压缩为：

```text
登录逻辑里可能存在问题。
```

而应该保存：

```text
文件：src/auth/token.ts
符号：parseToken()
事实：第 84 行把毫秒时间戳按秒处理
证据：auth.spec.ts 的 expired-token 用例失败
```

代码可以重新读取，但定位和结论不能丢。

---

### 3. Browser Use / Computer Use：压缩页面历史，保留动作账本

环境操作产生的截图、DOM 和 Accessibility Tree 很容易占满 Context。

Runtime 可以只保留：

```text
当前页面或窗口
任务相关控件
已填写字段
最近一次关键观察
已执行动作
是否提交成功
下一步动作
```

旧截图和完整 DOM 存入 Artifact Store。

特别需要保留幂等状态：

```text
提交按钮已点击
尚未收到成功回执
不要再次点击，先检查订单列表
```

否则压缩后 Agent 可能重复付款、重复发消息或重复提交表单。

---

### 4. MCP：工具结果由 Host Runtime 决定如何进入 Context

MCP Server 可能返回长文档、数据库记录、日志或网页内容。

协议负责交换工具和资源，但不应该默认把所有返回值永久放入模型上下文。

Host Runtime 可以：

```text
提取当前任务相关字段
保留 resource URI 或 artifact_id
对长结果生成可验证摘要
移除已经消费且不再需要的工具结果
需要时再次调用 Resource 或 Tool
```

同时要保留工具调用与结果之间的对应关系，避免消息结构失效。

---

### 5. A2A：压缩成最小任务交接包

Agent 间协作时，不应该把全部聊天历史发送给下一个 Agent。

更合理的是生成 Handoff Context：

```json
{
  "task": "检查支付回调的幂等实现",
  "constraints": ["不要修改对外接口"],
  "confirmed_facts": ["重复请求来自两个 Worker"],
  "artifacts": ["src/payment/callback.ts"],
  "expected_output": "根因、修改建议和验证用例",
  "acceptance_criteria": ["并发重试只处理一次"]
}
```

这既减少 Token，也降低不同 Agent 之间的状态污染。

---

### 6. ACP：围绕编辑器工作集动态压缩

在 ACP 或编辑器 Agent 场景中，Context 可以优先保留：

```text
当前文件和选区
相关符号定义
当前 diff
诊断信息
任务计划
工作区规则
```

已经关闭且与当前任务无关的文件，可以从 Context 中移除，但保留路径和索引。

这本质上是根据用户当前编辑状态动态编译 Context，而不是把整个仓库持续塞给模型。

---

### 7. Provider 原生 Compaction 与自定义压缩结合

部分模型平台提供服务端 Compaction，可以在上下文达到阈值后自动生成压缩状态。

它适合处理通用的长会话连续性。

但业务 Runtime 仍然需要维护：

```text
结构化任务 State
用户硬约束
权限和安全边界
Artifact 引用
执行历史和审计记录
领域相关的保留策略
```

平台 Compaction 解决“模型如何继续对话”，业务压缩策略解决“系统如何可靠地继续执行任务”。

---

### 8. 用任务结果评估压缩质量

不能只看压缩率。

更有价值的指标包括：

```text
硬约束保留率
关键事实召回率
压缩前后任务成功率
重复工具调用次数
错误恢复成功率
平均输入 Token
延迟和成本
人工审计可追溯性
```

最重要的问题是：

```text
压缩以后，Agent 是否仍然能做出与压缩前一致的正确决策？
```

## 常见误区

### 误区一：上下文压缩就是删除最早的消息

时间顺序不是重要性顺序。最早的用户约束可能必须一直保留。

### 误区二：使用一个大模型总结全部聊天就够了

自由文本摘要容易遗漏 ID、路径、金额、状态和不确定性。关键内容需要结构化提取。

### 误区三：Context Window 足够大就不需要压缩

更大的窗口仍然会增加成本、延迟和噪声。能放进去不代表应该全部放进去。

### 误区四：只保留结论，不保留来源

没有来源的结论无法验证，也容易把模型假设误认为工具事实。

### 误区五：把代码、日志和截图全部改写成摘要

原始内容应该保存在外部存储中，Context 里保留引用和定位信息，以便按需恢复。

### 误区六：压缩后不做校验

摘要可能丢失硬约束、破坏工具调用顺序或遗漏未完成动作。压缩结果需要验证。

### 误区七：所有 Agent 使用同一份压缩上下文

不同 Agent 的任务、权限和输入需求不同，应生成最小必要的任务交接 Context。

### 误区八：把压缩后的内容直接写入 Long-Term Memory

压缩摘要主要服务当前任务。只有稳定、经过确认、未来可复用的信息，才适合进入长期记忆。

## 面试加分答案

如果面试官问：

> Agent 如何做上下文压缩？

可以这样回答：

```text
Agent 的上下文压缩，不是简单截断历史，而是在有限 Context Budget 下保留继续完成任务所必需的信息。

我会先由 Runtime 维护明确的预算和触发阈值，再把信息分成几类：目标和硬约束原样保留；事实、决策、失败方案和下一步动作提取到结构化 Working Memory；旧对话和执行过程做任务型摘要；代码、网页、截图和长日志保存到 Artifact Store，Context 中只保留引用和关键定位；被移出的信息通过 Retrieval 按需找回。

压缩策略通常会组合使用滑动窗口、选择性保留、结构化状态提取、分阶段摘要、工具结果清理和外部化存储。压缩后还要验证目标、约束、关键 ID、未完成动作以及工具调用与结果是否完整，避免摘要漂移。

在 AI Coding 中，我会保留当前 diff、相关符号、测试结论和文件引用，而不是长期携带完整代码；在 Browser Use 和 Computer Use 中，重点保留当前页面状态、动作账本和是否提交成功；MCP 的长工具结果由 Host Runtime 摘要或外部化；A2A 只传递最小任务交接包；ACP 则根据当前文件、选区、诊断和工作区规则动态编译 Context。

所以，好的上下文压缩不是让内容尽可能短，而是让 Agent 在更少 Token 下仍然知道目标、约束、事实、证据、进度和下一步，并且在需要时能恢复原始信息。
```

---

## 一句话总结

上下文压缩是 Agent Runtime 在有限 Token 预算内，对目标、约束、状态、证据和历史信息进行保留、提取、摘要、外部化与按需恢复的过程。
