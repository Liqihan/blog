# Agent 面试知识点 #018：Agent 如何管理长期知识？

## 摘要

Agent 完成一次任务后，通常会产生很多以后可能复用的信息：

```text
项目使用 pnpm，而不是 npm
支付回调必须使用 event_id 做幂等
某个页面提交后不会立即出现成功提示
代码提交前必须执行 lint 和单元测试
某类故障过去已经验证过三个无效方案
```

如果这些信息只留在当前对话里，任务结束后就会消失。

但如果把所有聊天、日志和工具结果都永久保存，长期知识库又会迅速变成一个充满重复、过期和冲突信息的垃圾场。

所以 Agent 管理长期知识的核心不是“记得更多”，而是：

```text
把值得复用的信息沉淀下来，
并在未来任务中准确、可控、可验证地重新使用。
```

这需要完整的知识生命周期，而不只是一个向量数据库。

---

## 问题

Agent 如何管理长期知识？

长期知识和 Long-Term Memory、RAG、模型参数分别是什么关系？

为什么知识管理最终会变成 Runtime、数据库和治理问题？

---

## 面试官在考什么？

这个问题表面上是在问 Agent 如何保存知识。

但面试官真正想考的是：

> 你是否能够设计一套可持续运行的知识系统，让 Agent 知道什么值得写入、如何找到、怎样验证，以及什么时候更新或删除。

一个最简单的实现通常是：

```text
把对话切块
生成 Embedding
写入向量数据库
下一次按相似度检索
```

这个方案很快会遇到问题：

```text
一次性信息被误认为长期规则
旧版本知识覆盖新版本事实
相似内容很多，但真正有用的排在后面
模型推测和工具事实混在一起
不同用户、项目和组织的数据互相污染
知识来源消失，无法判断是否可信
```

因此，长期知识管理考察的不是“会不会做 RAG”，而是是否理解知识的写入、检索、版本、权限、时效和反馈闭环。

---

## 核心知识点

### 1. 长期知识不是完整历史

长期知识是从历史交互、工具执行和外部资料中提炼出的可复用信息。

```text
原始历史：某次任务的完整对话、日志和页面截图
长期知识：经过验证、未来仍可能复用的事实、规则和经验
```

例如：

```text
原始记录：Agent 连续三次使用 npm 安装依赖都失败，随后读取 package.json，确认项目使用 pnpm。

长期知识：该仓库使用 pnpm，执行依赖相关任务前应优先读取 packageManager 字段验证。
```

长期知识不是历史的副本，而是历史经过筛选、归纳和验证后的结果。

---

### 2. 长期知识需要分类

常见知识类型可以分为：

```text
事实知识：项目、用户、系统和业务的稳定事实
流程知识：完成某类任务的步骤、约束和验收标准
经验知识：过去任务中的成功方案、失败方案和原因
偏好知识：用户明确确认的长期偏好
外部知识：文档、代码、数据库和网页中的领域资料
```

例如 AI Coding 场景中：

```text
事实：仓库使用 TypeScript
流程：提交前运行 pnpm lint && pnpm test
经验：修改生成目录会在构建时被覆盖
外部知识：架构文档、ADR、README 和代码实现
```

不同类型的知识，写入方式和有效期不同，不能全部用同一种规则处理。

---

### 3. 每条知识都需要元数据

只有一段自然语言文本，无法支撑可靠治理。

一条长期知识至少应该记录：

```json
{
  "type": "project_rule",
  "content": "提交前必须运行 pnpm lint",
  "scope": "repo:groveLqh/blog",
  "source": "AGENTS.md",
  "source_version": "commit:abc123",
  "confidence": 0.99,
  "valid_from": "2026-07-15",
  "status": "active",
  "permissions": ["repo_member"]
}
```

关键字段包括：

```text
来源：这条知识从哪里来
作用域：属于哪个用户、项目或组织
版本：对应哪个时间点或代码版本
置信度：是工具事实、用户确认，还是模型推测
状态：有效、待验证、已废弃或已冲突
权限：哪些 Agent 和用户可以读取
```

没有元数据的知识，只能被检索，不能被真正管理。

---

### 4. 写入比检索更重要

长期知识系统最危险的错误，不是少记一条，而是把错误信息长期保存。

一个可靠的写入流程通常包括：

```text
产生候选知识
判断未来是否可复用
识别知识类型和作用域
验证来源和证据
检查重复与冲突
写入新记录或更新旧记录
记录版本和审计信息
```

知识写入可以分为两种：

```text
显式写入：用户确认“记住这个规则”
隐式沉淀：任务结束后，Runtime 从结果中提取候选知识
```

隐式沉淀不应该直接成为高置信度事实，最好先进入待验证状态，或通过规则、工具结果和人工确认提高可信度。

---

### 5. 检索不是只做向量相似度

Agent 检索长期知识时，通常需要组合：

```text
关键词检索
向量检索
结构化字段过滤
作用域过滤
时间与版本过滤
权限过滤
Rerank
```

例如 Agent 修复一个支付问题时，查询条件不只是“支付重复”。

它还需要限制：

```text
当前代码仓库
当前分支或版本
支付模块
仍处于 active 状态
当前 Agent 有权限读取
```

真正的检索流程更像：

```text
理解当前任务
生成检索计划
召回候选知识
过滤过期和越权内容
按相关性与可信度排序
把少量结果放入 Context
```

所以长期知识库负责保存，Context Manager 负责决定本轮模型真正看到什么。

---

### 6. 知识必须支持更新、冲突和遗忘

长期不等于永久正确。

例如：

```text
项目从 npm 迁移到 pnpm
旧接口已经废弃
业务流程发生变化
网页结构已经改版
过去成功的方案不再适用于新版本
```

系统需要支持：

```text
版本更新
新旧知识关联
冲突检测
降低置信度
标记废弃
TTL 或有效期
显式删除
按用户或项目清空
```

发生冲突时，不应该简单保留两段文本让模型自己猜。

Runtime 应该优先比较来源、版本、时间和可信度，并在无法判断时把冲突暴露出来。

---

### 7. 长期知识必须和原始证据分离

知识记录应该尽量简洁，但原始证据需要可追溯。

例如：

```text
知识：并发请求必须使用分布式幂等锁
证据：故障报告、测试日志、代码提交和架构决策记录
```

原始代码、网页、截图和长日志可以保存在 Artifact Store、文件系统或文档库中。

长期知识只保存：

```text
结论
来源引用
关键位置
版本信息
验证状态
```

这样既能控制 Context 大小，也能在关键决策前重新读取原始证据。

## 工业界方案

### 1. Runtime 建立独立的 Knowledge Service

成熟系统通常会把长期知识能力从模型调用中拆出来：

```text
对话、工具结果、任务产物
          ↓
Knowledge Extractor
          ↓
Validator / Deduplicator
          ↓
Knowledge Store + Search Index
          ↓
Retriever / Reranker
          ↓
Context Manager
          ↓
Model
```

Knowledge Service 负责写入、版本、权限、检索和删除。

Agent Runtime 负责在任务开始、阶段切换和工具调用后决定何时读写知识。

---

### 2. AI Coding 与 ACP：以仓库为知识作用域

AI Coding Agent 的长期知识可以来自：

```text
README、AGENTS.md 和设计文档
ADR 和历史提交
代码符号与依赖关系
测试命令与构建规则
过去故障和修复经验
```

在 ACP 或编辑器场景中，用户切换工作区时，Runtime 应切换对应的项目知识空间。

同时，代码本身仍然是 Source of Truth。

如果长期知识说项目使用 npm，但当前 `package.json` 已声明 pnpm，Agent 应以当前代码为准并更新旧知识。

---

### 3. MCP：提供知识访问能力，不替代知识治理

MCP Resource 可以把文件、数据库、文档库等信息以标准 URI 暴露给 Host。

也可以提供：

```text
knowledge.search
knowledge.read
knowledge.write_candidate
knowledge.invalidate
```

但 MCP 只解决能力和数据如何被访问。

哪些内容值得长期保存、如何做权限隔离、检索结果是否进入 Context，仍然由 Host Runtime 决定。

---

### 4. A2A：传递知识引用，不复制全部知识库

Agent 间协作时，应该传递当前子任务需要的最小知识包：

```json
{
  "task": "检查支付回调幂等性",
  "facts": ["重复请求来自不同 Worker"],
  "constraints": ["保持外部 API 兼容"],
  "knowledge_refs": ["kb://payment/idempotency/v3"],
  "artifacts": ["repo://src/payment/callback.ts"]
}
```

子 Agent 不需要读取主 Agent 的全部长期知识，也不应该默认把自己的全部记忆写回共享空间。

共享知识要遵循最小必要和明确授权原则。

---

### 5. Browser Use / Computer Use：沉淀规则，不保存全部现场

环境操作会产生大量截图、DOM、Accessibility Tree 和临时状态。

真正适合沉淀的通常是：

```text
稳定入口和页面规则
经过验证的操作流程
重复出现的兼容性问题
提交前必须满足的条件
用户明确确认的默认选项
```

不适合长期保存的是：

```text
一次性验证码
当前鼠标位置
临时弹窗
短期页面状态
凭证和敏感信息
```

对于网页知识，还应该保存来源 URL、抓取时间和版本标识，避免 Agent 长期使用已经失效的页面规则。

---

### 6. AI Native Software：把知识层做成产品基础设施

在 AI Native Software 中，知识不应该只藏在 Prompt 里。

更合理的设计是建立统一知识层：

```text
用户知识
项目知识
组织知识
领域知识
任务经验
外部数据源
```

不同 Agent 通过统一的检索、权限和审计机制访问它。

模型可以更换，Agent 可以拆分，协议可以升级，但经过治理的知识资产仍然可以持续复用。

---

## 常见误区

### 误区一：把所有对话都写入长期知识库

完整历史包含大量临时信息。长期知识应该经过筛选、验证和结构化。

### 误区二：有向量数据库就等于有知识管理

向量数据库只解决部分召回问题，不能自动处理作用域、版本、权限、冲突和删除。

### 误区三：检索到的内容都直接放进 Context

检索结果还需要过滤、排序、去重和预算控制。召回不等于使用。

### 误区四：把模型总结当成事实

模型生成的结论需要保留来源和置信度，不能自动升级为已验证知识。

### 误区五：知识写入后永久不变

代码、业务和网页都会变化。长期知识必须支持更新、失效和遗忘。

### 误区六：不同 Agent 共享全部知识

不同 Agent 的任务和权限不同。知识共享应该有作用域和最小必要边界。

### 误区七：长期知识可以替代实时工具调用

长期知识提供先验，实时工具和当前环境才是最新事实。关键决策前仍需要重新验证。

## 面试加分答案

如果面试官问：

> Agent 如何管理长期知识？

可以这样回答：

```text
Agent 管理长期知识，不是把全部聊天记录写进向量数据库，而是建立一套完整的知识生命周期。

首先要区分事实、流程、经验、偏好和外部知识，并给每条知识记录来源、作用域、版本、置信度、有效状态和权限。写入时需要判断是否可复用，进行验证、去重和冲突检测；检索时不能只做向量相似度，还要结合关键词、元数据、时间、版本、权限和 Rerank，只把当前任务真正需要的少量知识放入 Context。

长期知识还必须支持更新、废弃、TTL 和删除。模型生成的总结只能先作为候选知识，代码、数据库、用户确认和工具结果等可验证来源应具有更高优先级。

在 AI Coding 和 ACP 场景里，我会以仓库或工作区作为知识作用域，并始终用当前代码验证旧知识；MCP 可以标准化知识资源和搜索工具的访问方式，但知识治理仍由 Host Runtime 负责；A2A 只传递子任务需要的知识引用和证据；Browser Use 与 Computer Use 只沉淀稳定规则和流程，不保存一次性页面状态与敏感信息。

所以真正可靠的长期知识系统，本质上是 Knowledge Store、Search Index、Artifact Store、权限系统和 Context Manager 共同组成的数据基础设施，而不是模型自身记忆能力的简单延伸。
```

---

## 一句话总结

Agent 管理长期知识的关键，是让可复用信息有来源、有作用域、有版本、可检索、可验证、可更新，也可以被安全地遗忘。
