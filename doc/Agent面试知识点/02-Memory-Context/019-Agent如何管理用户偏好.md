# Agent 面试知识点 #019：Agent 如何管理用户偏好？

## 摘要

用户偏好决定了 Agent 应该“怎么做”，而不只是“做什么”。

例如：

```text
回答先给结论，再展开分析
技术文章不要写成营销号风格
代码修改尽量保持最小 diff
提交前运行 lint 和测试
默认使用中文，但代码和术语保留英文
涉及付款或提交操作时必须再次确认
```

这些信息如果每次都让用户重新说明，Agent 会显得没有连续性。

但如果 Agent 把所有表达都永久记住，也会产生新的问题：

```text
一次性要求被误认为长期偏好
旧偏好覆盖用户当前明确指令
模型根据几次行为过度推断用户习惯
不同项目的规则互相污染
敏感信息被不必要地长期保存
用户不知道系统记住了什么，也无法纠正
```

所以，用户偏好管理的核心不是“记得越多越好”，而是：

```text
只记值得长期复用的偏好，
在正确的作用域内使用，
并且始终允许当前指令覆盖、用户查看和修改。
```

---

## 问题

Agent 如何管理用户偏好？

用户偏好和 Long-Term Memory、Profile、Context、项目规则有什么区别？

显式偏好与隐式推断应该如何写入、更新、冲突处理和删除？

---

## 面试官在考什么？

这个问题表面上是在问个性化。

但面试官真正想考的是：

> 你是否能够把用户偏好设计成一套可解释、可覆盖、可治理的长期状态，而不是把几句自然语言永久塞进 Prompt。

一个简单实现可能是：

```text
用户说过“以后都简短一点”
↓
写入数据库
↓
每次调用都拼进 System Prompt
```

这个方案很快会遇到问题：

```text
用户只是在某次任务中要求简短
不同场景对“简短”的定义不同
当前任务明确要求详细，但旧偏好仍然生效
偏好越来越多，Prompt 越来越长
偏好之间发生冲突，却没有优先级
```

因此，偏好管理最终会变成 Memory、Context、Runtime、权限和交互设计的综合问题。

---

## 核心知识点

### 1. 用户偏好描述的是“选择倾向”，不是客观事实

长期知识通常回答：

```text
这个项目使用什么技术栈？
这个接口有什么约束？
过去发生过什么？
```

用户偏好回答的是：

```text
用户更希望系统如何表达、选择和执行？
```

常见类型包括：

```text
表达偏好：语言、语气、长度、结构、术语风格
决策偏好：更重视速度、成本、稳定性还是可维护性
执行偏好：是否自动操作、何时确认、默认工具和流程
内容偏好：关注的话题、避免的话题、推荐范围
项目偏好：代码风格、提交方式、测试要求、文档格式
界面偏好：布局、主题、默认视图和交互方式
```

偏好不是永恒真理，而是可变化、可覆盖的选择倾向。

---

### 2. 必须区分显式偏好和隐式推断

显式偏好来自用户直接表达：

```text
以后技术文章先给结论
这个仓库统一使用 pnpm
提交前一定先让我确认
```

隐式偏好来自系统对行为的观察：

```text
用户连续多次选择表格而不是长段落
用户经常拒绝过度正式的语气
用户在代码任务中总是选择最小改动方案
```

两者不能具有相同权重。

一般可以采用：

```text
用户明确确认 > 当前任务指令 > 项目规则 > 高置信度历史偏好 > 模型推断
```

隐式推断最好先作为候选偏好，而不是直接成为长期规则。

---

### 3. 一次性要求不等于长期偏好

用户在当前任务中说：

```text
这次只给我一段话
今天先不要展开技术细节
这个文件先不要运行测试
```

这些通常属于当前任务约束，而不是长期偏好。

判断是否值得长期保存，可以看：

```text
用户是否使用“以后、默认、每次、从现在开始”等长期表达？
该选择是否在多个任务中重复出现？
未来是否具有稳定复用价值？
错误记住后会不会带来较大副作用？
是否需要用户确认？
```

对高影响偏好，例如自动发送、付款确认、删除策略和权限边界，不能仅靠模型推断。

---

### 4. 偏好需要明确作用域

同一个用户在不同场景中的偏好可能完全不同。

例如：

```text
个人聊天：语气轻松
技术报告：结构严谨
代码仓库 A：使用 pnpm
代码仓库 B：使用 npm
内部文档：中文
开源 README：英文
```

因此偏好至少需要区分：

```text
用户级：跨任务通用的表达和交互偏好
项目级：当前仓库、工作区或业务的规则
任务级：本次任务临时要求
工具级：某个应用或工具的默认行为
组织级：团队统一规范和安全策略
```

没有作用域的偏好，很容易污染其他任务。

---

### 5. 每条偏好都需要来源、置信度和状态

一条可治理的偏好记录可以包含：

```json
{
  "type": "response_style",
  "key": "answer_structure",
  "value": "conclusion_first",
  "scope": "user",
  "source": "explicit_user_instruction",
  "confidence": 1.0,
  "status": "active",
  "created_at": "2026-07-16T10:00:00+08:00",
  "updated_at": "2026-07-16T10:00:00+08:00"
}
```

关键字段包括：

```text
key/value：偏好是什么
scope：在哪个范围内生效
source：用户确认、行为推断还是系统规则
confidence：可信程度
status：候选、有效、已废弃或冲突
时间：何时创建和最近更新
```

只有一段自然语言文本，很难做冲突处理和精确应用。

---

### 6. 当前明确指令必须能够覆盖长期偏好

偏好应该是默认值，而不是不可违反的规则。

例如用户长期偏好简洁回答，但本轮明确要求：

```text
请完整展开，给我一份系统报告。
```

本轮指令应该优先。

可以把优先级设计为：

```text
安全和权限规则
> 当前用户明确指令
> 当前项目或组织规则
> 用户确认的长期偏好
> 高置信度推断偏好
> 系统默认值
```

如果两个同级偏好冲突，Runtime 应根据作用域、更新时间和来源决定，无法判断时不应静默猜测。

---

### 7. 偏好不应该全部塞进每一轮 Context

用户可能积累很多偏好：

```text
写作风格
代码习惯
旅行偏好
图像审美
工具使用方式
通知设置
```

当前是代码任务时，没有必要加载旅行和图像偏好。

更合理的流程是：

```text
识别当前任务类型
按用户、项目和工具作用域过滤
召回少量相关偏好
解决冲突并排序
编译为本轮可执行约束
放入 Model Context
```

偏好库负责保存，Context Manager 负责按需应用。

---

### 8. 用户必须能够查看、纠正和删除偏好

模型可能误解用户，也可能把临时要求错误沉淀。

因此系统应该支持：

```text
查看系统当前记住的偏好
解释某个行为使用了哪条偏好
修改偏好内容和作用域
临时关闭个性化
删除单条或全部偏好
标记“这次不要记住”
```

用户偏好管理不仅是后端数据问题，也是产品信任问题。

一个无法解释“为什么这样回答”的个性化系统，很容易让用户觉得不可控。

---

## 工业界方案

### 1. Runtime 建立独立的 Preference Service

成熟系统通常会把偏好从普通对话历史中拆出来：

```text
用户表达与行为
      ↓
Preference Candidate Extractor
      ↓
Scope / Risk / Confidence Classifier
      ↓
Preference Store
      ↓
Resolver + Policy Engine
      ↓
Context Compiler
      ↓
Model / Agent
```

其中：

```text
Extractor：提取候选偏好
Classifier：判断类型、作用域、风险和可信度
Store：保存版本、来源和状态
Resolver：处理覆盖、冲突和失效
Policy Engine：保证安全与组织规则优先
Context Compiler：只加载本轮相关偏好
```

模型负责理解自然语言，Runtime 负责决定偏好是否真正生效。

---

### 2. 使用“Profile + Preference Events”双层模型

一种常见设计是同时维护：

```text
Current Profile：当前生效的结构化偏好快照
Preference Events：偏好的新增、修改、覆盖和删除记录
```

例如：

```text
事件 1：用户明确要求默认中文
事件 2：某个英文项目中要求 README 使用英文
事件 3：用户删除“所有回答必须简短”的偏好
```

Profile 方便快速读取，Events 方便追踪来源、回滚和审计。

这比直接覆盖一段用户画像更可靠。

---

### 3. AI Coding 与 ACP：区分个人习惯和仓库规则

AI Coding Agent 常见偏好包括：

```text
优先最小 diff
避免无关重构
测试失败时先定位根因
提交前运行指定命令
代码解释先讲调用链
```

但仓库里的 `AGENTS.md`、README、lint 配置和测试脚本通常比个人习惯优先级更高。

在 ACP 或编辑器场景中，可以按以下层次编译：

```text
组织安全规则
当前工作区规则
当前任务指令
用户编码偏好
编辑器默认设置
```

这样既能个性化，又不会让个人偏好破坏项目约束。

---

### 4. MCP：把偏好作为受控资源或工具能力

MCP 场景中，可以提供：

```text
preferences.search
preferences.get
preferences.propose
preferences.update
preferences.delete
```

但 MCP Server 不应该默认获得用户全部偏好。

Host 需要控制：

```text
当前 Server 可以读取哪些作用域
哪些敏感字段不可暴露
写入是否需要用户确认
返回结果是否进入模型 Context
```

协议负责能力交换，权限、应用和治理仍然属于 Host Runtime。

---

### 5. A2A：传递任务相关偏好，不共享完整用户画像

Agent 间协作时，只需要传递子任务真正相关的偏好。

例如代码审查 Agent 可以收到：

```json
{
  "task": "审查当前 diff",
  "preferences": [
    "优先关注隐藏副作用和兼容性风险",
    "按严重程度排序",
    "避免无关风格建议"
  ]
}
```

它不需要知道用户的其他写作、消费或界面偏好。

A2A Handoff 应遵循最小必要原则，防止隐私扩散和角色污染。

---

### 6. Browser Use / Computer Use：高风险执行偏好必须显式确认

环境操作中常见偏好包括：

```text
默认下载到哪个目录
表单中常用的非敏感选项
是否自动保存草稿
提交前是否需要确认
遇到弹窗时默认如何处理
```

但以下内容不能仅凭历史行为自动推断：

```text
付款和转账是否自动执行
是否发送消息或邮件
是否删除文件和记录
是否接受协议或授权
是否保存密码、验证码和身份信息
```

高风险行为应该由安全策略和当前确认决定，而不是由便利性偏好决定。

---

### 7. AI Native Software：让偏好成为可见的产品状态

在 AI Native Software 中，偏好不应该只隐藏在 Prompt 或模型记忆里。

产品可以提供：

```text
偏好中心
项目级覆盖设置
本次任务临时覆盖
记忆来源说明
最近使用记录
一键删除和关闭个性化
```

当 Agent 根据偏好改变行为时，可以在必要场景说明：

```text
“按照你在该项目中的设置，我会优先采用最小改动方案。”
```

这种可见、可改、可追溯的状态，比不可解释的“模型更懂你”更值得信任。

## 常见误区

### 误区一：用户说过一次，就应该永久记住

一次性任务要求不一定是长期偏好。需要判断表达、复用价值、作用域和风险。

### 误区二：根据行为推断的偏好和用户明确要求同等可信

隐式推断只能作为低置信度候选，不能覆盖用户当前明确指令。

### 误区三：把所有偏好拼进 System Prompt

偏好会不断增长，也与任务相关性不同。应该按作用域和当前任务动态检索。

### 误区四：偏好一旦写入就永久有效

用户和项目都会变化。偏好需要更新、版本、失效和删除机制。

### 误区五：个人偏好可以覆盖组织与安全规则

偏好只是默认选择，不能突破权限、安全、合规和项目硬约束。

### 误区六：所有 Agent 都应该共享完整用户画像

不同 Agent 只应获得完成当前任务所需的最小偏好集合。

### 误区七：个性化越强越好

过度个性化会放大错误推断、形成信息茧房，并让用户失去控制感。

### 误区八：用户偏好只属于后端 Memory 问题

它还涉及产品交互、解释能力、隐私、权限和用户纠错机制。

## 面试加分答案

如果面试官问：

> Agent 如何管理用户偏好？

可以这样回答：

```text
Agent 管理用户偏好，不能简单地把用户说过的话永久写入 Memory，而应该把偏好设计成带有类型、作用域、来源、置信度、状态和版本的结构化长期状态。

首先要区分显式偏好与隐式推断。用户明确确认的偏好权重更高，行为推断只能先作为候选；同时要区分用户级、项目级、任务级、工具级和组织级作用域，避免一个场景的规则污染其他场景。当前用户明确指令必须能够覆盖长期偏好，安全和组织规则则始终具有更高优先级。

工程上我会建立 Preference Service，包含候选提取、风险与作用域分类、Preference Store、冲突 Resolver、Policy Engine 和 Context Compiler。偏好不会全部进入每轮 Prompt，而是根据当前任务按需检索，只编译成少量可执行约束。系统还要支持查看、解释、修改、临时关闭和删除，让用户知道系统记住了什么以及为什么这样行动。

在 AI Coding 和 ACP 场景中，要区分个人编码习惯与仓库规则；MCP 可以暴露受控的偏好读写能力，但 Host 负责权限和确认；A2A 只传递子任务需要的最小偏好集合；Browser Use 和 Computer Use 中，普通默认选项可以复用，但付款、发送、删除和授权等高风险动作不能通过隐式偏好自动执行。

所以，用户偏好管理的目标不是让 Agent 盲目迎合用户，而是在可控、可解释和安全的边界内，减少重复沟通并提供稳定的个性化体验。
```

---

## 一句话总结

Agent 管理用户偏好的关键，是把偏好作为可作用域、可覆盖、可解释、可更新和可删除的长期状态，而不是把用户历史永久固化成不可控的 Prompt。
