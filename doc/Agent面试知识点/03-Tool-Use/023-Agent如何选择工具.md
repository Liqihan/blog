# Agent 面试知识点 #023：Agent 如何选择工具？

## 摘要

当 Agent 同时拥有搜索、数据库、代码执行、MCP、Browser Use、Computer Use 和子 Agent 等能力时，真正困难的不是“能不能调用”，而是：

```text
当前任务是否需要工具？
应该选哪一个？
多个工具都能完成时，哪个更可靠？
失败后应该重试、换工具，还是停止？
```

例如用户要求：

```text
确认仓库中的登录问题，修复后运行测试。
```

Agent 可能需要依次选择：

```text
search_code → read_file → apply_patch → run_tests → git_diff
```

它不能只根据关键词匹配工具名，而要结合任务阶段、工具边界、权限、风险和上一步结果做决策。

所以，Tool Selection 本质上是 Agent Runtime 中的一次受约束路由：

```text
理解目标 → 判断是否需要工具 → 召回候选
→ 策略过滤 → 选择并执行 → 根据结果重新规划
```

---

## 问题

Agent 如何选择工具？

为什么 Tool Description、Context、State、权限、成本和风险都会影响选择？

在 API、MCP、Browser Use、Computer Use、AI Coding Tool 和 A2A Agent 之间，应该如何确定优先级？

---

## 面试官在考什么？

这个问题表面上是在问模型如何挑选函数。

但面试官真正想考的是：

> 你是否理解工具选择由候选发现、语义匹配、策略过滤、执行校验和结果反馈共同组成，而不是把全部工具塞进 Prompt 后让模型自由决定。

工具少、差异明显时，模型直接选择通常能工作。进入生产后则会遇到：

```text
多个工具功能重叠
工具列表过大，占用 Context
工具描述模糊，模型容易误选
部分工具当前用户没有权限
Browser Use 能做，但 API 更稳定
高风险写操作必须确认
```

因此，工具选择能力不仅取决于模型，也取决于 Runtime 是否给模型提供了正确、有限且可执行的候选集合。

---

## 核心知识点

### 1. 第一个决策是“是否需要工具”

以下任务通常必须调用工具：

```text
查询实时或私有数据
读取当前文件、网页或系统状态
执行精确计算、代码或测试
发送、提交、删除等真实操作
验证模型无法凭自身知识确认的事实
```

解释稳定概念、改写用户已提供的文本、总结当前 Context，则可能不需要工具。

如果没有 `tool / no-tool` 判断，Agent 要么在需要真实数据时编造答案，要么对简单问题反复调用工具，增加延迟、成本和风险。

---

### 2. 候选发现和最终选择应该分开

工具只有几个时，可以全部提供给模型；当工具来自多个 MCP Server，数量达到几十甚至几百时，全部加载会造成：

```text
Schema 占用大量 Context
相似工具互相干扰
无关能力扩大权限暴露面
```

更合理的流程是：

```text
Tool Registry / Tool Search
        ↓
按任务、命名空间和工作区召回候选
        ↓
按权限、风险和可用性过滤
        ↓
模型在少量候选中选择
```

发现解决“有哪些工具可能有用”，选择解决“当前到底用哪个”。

---

### 3. Tool Description 和 Schema 是模型的语义接口

模型通常看不到真实实现，只能看到：

```text
name + description + inputSchema + outputSchema + annotations
```

因此描述不能只写“搜索内容”，而应说明：

```text
工具能做什么、不能做什么
什么时候使用
与相似工具有什么区别
是否只读、是否有副作用
成功结果代表什么
```

例如：

```text
search_repository：在指定仓库中按文件名、符号或文本定位代码；
只负责搜索，不读取完整文件，也不修改内容。
```

这样的描述能帮助模型区分 `search_repository`、`read_file` 和 `apply_patch`。Schema 过于复杂，也会让模型转向更容易调用但更不可靠的工具。

---

### 4. 工具选择是多目标决策，不只是相关性排序

语义最相关的工具，不一定是最终应该使用的工具。Runtime 还要考虑：

```text
能力是否匹配
数据是否足够新
历史成功率
用户是否有权限
是否存在不可逆副作用
执行成本与延迟
结果能否验证和审计
```

可以粗略理解为：

```text
工具价值
= 任务匹配度 + 可靠性 + 信息增益
- 成本 - 延迟 - 风险
```

但权限和安全属于硬约束，不能只靠打分。用户没有写权限时，即使写工具匹配度最高，也必须在策略层移除。

---

### 5. 选择必须结合 State 和 Context

同一句任务，在不同阶段需要不同工具：

```text
探索：search_code
定位：read_file
修改：apply_patch
验证：run_tests
收尾：git_diff
```

Tool Selection 的输入不能只有用户最新一句话，还要包括：

```text
当前目标和约束
已经调用过的工具
关键结果与错误
未完成步骤
副作用是否已经发生
剩余预算
```

否则 Agent 会重复搜索、未读取就修改、测试失败后仍提交，或者在操作已经成功后再次执行写工具。

---

### 6. 优先选择稳定、结构化、可验证的执行路径

多个路径都能完成任务时，常见优先级是：

```text
专用 API / 业务工具
> MCP 暴露的稳定语义工具
> Browser Use 的 DOM / Accessibility 操作
> Computer Use 的视觉与坐标操作
```

例如查询订单状态，结构化 `get_order` 通常优于打开后台页面再读取文字，因为 API 更容易返回明确状态、业务 ID 和错误码。

但很多系统没有 API，或者任务必须操作真实 UI，所以 Browser Use 和 Computer Use 仍然是必要的降级能力，而不是永远不该使用的工具。

---

### 7. 工具选择是持续闭环

工具执行后可能返回：

```text
参数错误、权限不足、数据为空、页面变化、超时或状态冲突
```

Agent 要根据错误类型重新选择：

```text
参数错误 → 修正参数
权限不足 → 停止并请求授权
API 不可用 → 在策略允许时降级到 Browser Use
写操作状态未知 → 先查询结果，不直接重试
```

因此真实流程是：

```text
Select → Execute → Observe → Re-select
```

可靠性来自整个闭环，而不是第一次就永远选对。

---

## 工业界方案

### 1. Tool Registry + 分层 Router

生产系统通常建立 Tool Registry，除模型可见的描述和 Schema 外，还记录：

```text
工具版本、命名空间、权限要求、风险等级
读写属性、成本、超时、成功率和降级路径
```

路由过程可以分为：

```text
Tool / No-Tool 判断
→ 候选工具检索
→ 权限与风险过滤
→ 模型选择或规则路由
→ 参数与业务校验
→ 执行和反馈
```

明确任务可以走规则，模糊任务可以让模型在有限候选中判断。

---

### 2. 动态加载工具与命名空间

工具很多时，可以先暴露高层领域：

```text
repository、browser、calendar、crm、billing
```

模型选定领域后，再加载少量具体工具。MCP Host 也可以只加载当前任务相关的 Server 或 Tool，而不是把所有已连接能力同时放进 Context。

动态加载能够减少 Token、名称冲突和权限暴露，并提升选择准确率。

---

### 3. AI Coding 与 ACP：按任务阶段开放能力

编辑器 Agent 可以按阶段提供工具：

```text
探索：list_files、search_code、read_file
修改：apply_patch、format_file
验证：run_tests、get_diagnostics、git_diff
提交：git_status、git_commit
```

ACP 或编辑器 Host 可以结合当前文件、选区、诊断和工作区权限动态启用工具。没有写权限时只提供读取与审查能力；进入提交阶段前，Runtime 必须确认测试和 Diff 状态。

---

### 4. Browser Use / Computer Use：建立降级链

环境操作通常按以下顺序选择：

```text
业务 API → 页面结构化接口
→ Browser DOM / Accessibility
→ Computer Use 视觉操作
```

每次降级都要重新评估准确性、风险和结果可验证性。Computer Use 最通用，但也更容易受到按钮位置、弹窗和界面变化影响，不能仅凭“点击成功”判断业务完成。

---

### 5. MCP 与 A2A 处在不同层级

MCP Tool 通常代表一个明确能力，例如查询数据库或创建 Issue。

A2A 面向可以自主规划、多轮执行并交付 Artifact 的另一个 Agent。

```text
选择 Tool：选择一种能力
选择 A2A Agent：选择一个任务承担者
```

任务边界清晰、输入输出确定时优先普通 Tool；需要独立 Context、专业推理或长时间执行时，再考虑交给另一个 Agent。

---

### 6. 用 Trace 和 Eval 优化工具选择

核心指标包括：

```text
Tool / No-Tool 判断准确率
首选工具正确率
候选召回率
无效与重复调用率
降级成功率
任务完成率
平均成本和延迟
高风险误调用拦截率
```

Trace 还要记录模型看到了哪些工具、哪些被策略过滤、最终为何选择、结果如何影响下一步。否则无法判断失败来自模型、工具描述、候选召回、权限策略还是执行器。

---

## 常见误区

### 误区一：把所有工具一次性提供给模型

工具越多不代表能力越强，反而会增加 Context 成本、冲突和权限风险。

### 误区二：工具选择完全交给 Prompt

Prompt 可以指导语义判断，但权限、风险和业务状态必须由 Runtime 强制控制。

### 误区三：最通用的工具就是最佳工具

无限制 Shell 或 Computer Use 很通用，但专用 API 通常更稳定、更便宜、更容易审计。

### 误区四：调用成功就说明选对了

底层工具返回成功，只代表某一步完成，不代表用户最终目标已经满足。

### 误区五：向量检索可以独立完成工具路由

语义检索只能召回候选，不能替代权限、状态、副作用和风险判断。

### 误区六：失败后不断换工具重试

重试和降级需要预算、停止条件和幂等控制，否则 Agent 会陷入高成本循环。

---

## 面试加分答案

如果面试官问：

> Agent 如何选择工具？

可以这样回答：

```text
Agent 选择工具不是关键词匹配，而是一个受约束的路由过程。首先判断当前任务是否需要工具，例如是否依赖实时数据、私有信息、精确计算或真实副作用；如果需要，再从 Tool Registry 或 MCP Server 中召回少量候选，而不是把全部工具一次性放进 Context。

最终选择要综合任务匹配度、可靠性、数据新鲜度、权限、风险、延迟、成本和结果可验证性。权限和安全是硬约束，由 Runtime 过滤；模型更适合负责自然语言理解、候选比较和参数生成。工具的名称、描述与 Schema 是模型理解能力边界的语义接口，必须明确何时使用、不能做什么，以及与相似工具的区别。

工具选择还要结合当前 State。AI Coding 在探索、修改、测试和提交阶段需要不同工具；Browser Use 和 Computer Use 应优先选择结构化 API，再逐级降级到 DOM 和视觉操作；MCP 用于调用标准化能力，A2A 则用于把完整子任务交给另一个 Agent。

执行结果会继续影响下一轮选择，因此完整流程是 Select、Execute、Observe、Re-select。生产系统通常采用 Tool Registry、候选检索、策略引擎、模型路由、执行校验和 Trace/Eval 组成的分层方案。

所以，好的 Tool Selection 不是让模型拥有最多工具，而是让它在当前状态下只看到有权限、低风险、最可靠且最能推进任务的那几个能力。
```

---

## 一句话总结

Agent 选择工具的核心，是在目标、状态、权限、风险、成本和可靠性约束下，为当前一步找到最小、最稳、最可验证的执行能力，并根据结果持续调整。
